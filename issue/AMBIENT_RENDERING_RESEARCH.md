# 常時演出の描画負荷：技術調査報告

調査日：2026-10-07。対象：作業ツリーの C# / .NET 10 / Avalonia 11.3.22。Fable は開発用エージェントの名称として扱う。これは改善候補の調査報告であり、確定仕様や実装済み変更ではない。アプリコード・設定・既存仕様は変更していない。今回、新たな実機ベンチマークは実施していない。

**結論：次に調べるべきは「静的な発光を毎回描く費用」「明滅が広げる更新範囲」「macOSソフトウェア描画の全画面転送」の三つ。** 背景の縮小キャッシュと30 fps化は実施済みであり、タイマーや位置計算だけの変更では大幅削減を期待しにくい。まず描画範囲を観察し、静的な枠の発光を画像化する比較実験を勧める。

## 1. 現状と測定値の読み方

`Program.cs` は Windows / macOS とも Software に固定。`CLAUDE.md` 冒頭などには古い「Mac = GPU」という記述も残るが、現状判断にはコードを優先した。調査で読んだ `AmbientAnimator.MinFrameMs` は30。設定「VSync」は別課題として変更中で、調査中にもモデル側への追加が見られたため、本報告は約30 fpsの構成を基準とし、その変更の完了状態は判定しない。

`issue/AMBIENT_CPU.md` の2026-10-07実装後の記録は次のとおり。Mac Retina、Release、Software、背景画像のキャッシュあり、約30 fps。今回の測定値ではない。

| 構成 | 記録されたCPU使用率 |
|---|---:|
| 全部オン・背景あり（玉2個＋強い明滅＋帯） | 30.1% |
| 全部オン・背景なし | 29.3% |
| 玉だけ・背景あり | 24.0% |
| 明滅だけ・背景あり | 22.7% |
| 動く帯だけ・背景あり | 16.1% |
| 演出なし・背景なし | 0.5% |
| 非表示 | 0.5〜0.6% |

この測定は表示3秒後から8秒間と記載されており、長時間平均の確証にはしない。全部オンの29.3%と30.1%から、背景画像は現在の第一候補ではない。単独効果の値を足して全部オンの値を予測することもできない。再描画や転送の共通費用がある。

MacのCPU%は1コア換算。Windowsタスクマネージャの総CPUに対する割合とは尺度が異なるため、過去のWindows 8.6%との数字だけの比較は避ける。過去のGPU/Software比較も当時の条件に対する結果で、あらゆる描画構成の優劣を確定するものではない。

## 2. コードから分かること

### 静的な枠の発光は、ピクセル画像としてはキャッシュされていない

対象：`src/FileLauncher.Desktop/Themes/NeonGlowLayer.cs:48` と `:97`、`src/FileLauncher.Core/Theming/NeonProfile.cs`。

`NeonGlowPlan` が保存するのは Geometry と Brush。`Draw()` は帯ごとに `DrawGeometry` を記録する。現在の `FlBoardGlow` と断面式から計算すると、外側53帯・内側29帯、計82個のリングになる（既定の影パラメータによる式の再計算。実機の描画回数を計測した数字ではない）。

**C#の `Render()` が毎フレーム呼ばれる、という意味ではない。** Avaloniaが保持する描画命令と、描画済みピクセルの保持は別物。変更範囲に重なる静的要素は、その描画命令が描画スレッドで再実行され得る。したがって「静的だからアニメーション中も描画費用ゼロ」は成立しない。[11.3.22の描画命令再生処理](https://github.com/AvaloniaUI/Avalonia/blob/11.3.22/src/Avalonia.Base/Rendering/Composition/Server/ServerCompositionDrawListVisual.cs)

### 明滅は画像化済みだが、画像の矩形が大きい

対象：`src/FileLauncher.Desktop/Effects/PulseLayer.cs:112`。

`PulseLayer.Refresh()` は発光を一度画像に焼く。一方 `Render()` は「盤面＋周囲40 DIPずつ」の画像全体を描き、`Level` の変更で無効化する。中央の透明画素が多くても、描画命令の矩形は大きい。明滅の更新時に盤面全体に近い範囲をdirtyにする有力な構造的理由になる。

既定の `DirtyRectTracker` は複数の更新矩形を一つの外接矩形にまとめる。対向する玉2個、離れた枠の辺などもまとめ方によって範囲が膨らむ。**明滅を四辺に分割するだけでは、この既定動作によって再び全体相当になり得る。** 分割と領域単位のdirty clippingは組み合わせて検証する必要がある。[11.3.22のDirtyRectTracker](https://github.com/AvaloniaUI/Avalonia/blob/11.3.22/src/Avalonia.Base/Rendering/Composition/Server/DirtyRectTracker.cs)

### 「Macでは常に窓全体の再描画」は精密な説明ではない

11.3.22の `ServerCompositionTarget` はdirty領域でクリップして描画する。描画先が前フレームを保持しない場合には中間レイヤーを使用し、その結果を描画先へ転送する。つまり、次の費用を区別する必要がある。

1. UIスレッドでの位置計算・描画命令の更新。
2. 描画スレッドでの図形描画・画像合成。
3. 描画済み結果の全体転送・OSでの表示。

画面全体の転送があっても、図形が常に全画面で再ラスタライズされるとは限らない。既存メモの「窓全体再描画」は観察に基づく仮説として扱い直すのが妥当。[11.3.22の描画ターゲット実装](https://github.com/AvaloniaUI/Avalonia/blob/11.3.22/src/Avalonia.Base/Rendering/Composition/Server/ServerCompositionTarget.cs)

### MacのSoftware経路には、毎フレーム全体を転送する費用がある

公式11.3.22ソースを取得して次を確認した。

- `TopLevelImpl.FramebufferRenderTarget.Lock()` は窓の物理ピクセル数に応じた `DeferredFramebuffer` を生成する。
- `DeferredFramebuffer` は `width × height × 4` バイトをネイティブ確保し、表示に渡した後に解放する。
- ネイティブ側 `setSwFrame` は、受け取ったフレームの各行を `memcpy` でIOSurfaceへコピーして表示する。ここにはdirty矩形の引数がない。

これはソースで確認できる固定費であり、今回のCPUの何%を占めるかは未測定。例として800×500 DIP、scale 2なら1枚6.4 MB、30 fpsでコピー1回分だけでも約192 MB/sになる。読み書き両方や中間描画の費用はこの数字に含めていない。帯域量だけで30%のCPUを説明できるわけではないが、小さな玉だけでも費用が残る理由にはなる。[TopLevelImpl](https://github.com/AvaloniaUI/Avalonia/blob/11.3.22/src/Avalonia.Native/TopLevelImpl.cs)、[DeferredFramebuffer](https://github.com/AvaloniaUI/Avalonia/blob/11.3.22/src/Avalonia.Native/DeferredFramebuffer.cs)、[ネイティブ転送処理](https://github.com/AvaloniaUI/Avalonia/blob/11.3.22/native/Avalonia.Native/src/OSX/rendertarget.mm)

### 玉と走査線の現状

`OrbLayer.Place()` は毎回 `Point[10]` と `TranslateTransform` を生成し、尾を更新して `InvalidateVisual()` する。芯＋暈＋尾のグラデーションも描画する。配列・Transformの再利用、暈の小さな画像化には余地がある。ただし、この割り当て量だけをCPU 20%台の主因とは判断できない。

`ScanBeamLayer` は既に不変ブラシと再利用する `TranslateTransform` で高さ60 DIPの矩形を動かしている。帯自体の実装は単純で、別のアニメーションAPIへの置き換えだけで大幅改善する根拠は薄い。上から帯を重ねるため、帯の裏にある静的要素の再描画費用も確認する。

静止した `ScanlineLayer` は別物。自分ではアニメーションを要求しないが、重なるdirty領域では横線の描画命令が再生され得る。静止走査線だけで常時負荷が増えると断定しない。

## 3. 改善案の優先順位

| 順位 | 対策 | 狙い・期待 | 制約 |
|---|---|---|---|
| 1 | 静的な `NeonGlowLayer` の画像キャッシュ | 多数のリングの再描画を画像合成へ置換。見た目を維持しやすく既存コードを共用できる | メモリ増。全体転送は残る。効果は実測が必要 |
| 2 | 明滅画像を四辺・角に分け、領域dirty clippingとセットで比較 | 透明な中央部分まで更新領域にする構造を避ける | 分割だけでは矩形unionで相殺。領域クリップ自体の費用もある |
| 3 | 静止した装飾を必要な単位で画像化 | 帯が通るたびにグリッド・走査線・発光を再描画する費用を削減 | 全UIの無条件画像化は入力・文字・更新管理を複雑にする |
| 4 | 玉の暈を小さな画像へ、配列とTransformを再利用 | グラデーション再描画と割り当てを削減 | 主因が共通転送なら小幅。尾の曲がり方を保つ必要あり |
| 5 | 最適化後の構成でGPU/Softwareを再比較 | ピクセル合成と転送の費用が大きい場合の改善余地 | 過去にGPUが遅かった事実は尊重。切替だけで改善するとはしない |
| 6 | Macで演出をCore Animationの独立レイヤーへ分離 | 演出だけの変化でAvaloniaの盤面を毎回描画・転送しない構成を目指す | 効果の上限は大きいが実装・保守費用も大。OS固有の技術検証が必要 |

**最初の実装候補は1。** `PulseLayer` が使う `NeonGlowPlan` を静的発光側でも画像化する。外側の発光は面の後ろ、内側は面の上という現在の重なり順を保つため、無条件に一枚へ統合しない。サイズ、DPI、色、影、面取り、枠寸法など見た目に影響する値が変わった時だけ焼き直す。`Render()` の途中で毎回画像を生成しない。

明滅の分割は、例えば中央を除いた上下左右の帯と角の画像で行う。各部品の実際の描画範囲を小さくする。見た目を変えずに合成量は減らせる可能性があるが、dirty領域の縮小効果は描画方式に依存する。

さらに必要なら、ぼけた暈だけを低解像度で作り、芯・枠線・文字はRetina解像度を維持する。両辺を半分にした暈の画像は画素数1/4だが、窓全体の転送画素数は変わらない。既存の発光輪郭や走査線ににじみが出ないかを確認する。

キャッシュの概算メモリは `幅DIP × 高さDIP × scale² × 4バイト`。800×500 DIP・scale 2なら一枚約6.1 MiBなので、「追加1 MB以下」という既存目標と両立するとは限らない。枠部分だけの画像や共有画像の利用も比較する。

## 4. Webで見かける対策をそのまま適用しない理由

**Compositionアニメーション：** 公式資料は描画スレッド上で動作することを説明している。UIスレッドの仕事は減らせるが、OSの独立した合成レイヤーに変わる保証ではない。今回のSoftware描画・全体転送も自動ではなくならない。無制限に動かして実描画fpsが30→60へ戻ると悪化する可能性もある。[Avalonia Composition animations](https://docs.avaloniaui.net/docs/graphics-animation/composition-animations)

**`CacheMode = BitmapCache`：** 現行Web資料には掲載されているが、調査対象の11.3.22公式ソースツリーとインストール済みAPI XMLではこの公開型・プロパティを確認できなかった。11.3.22にそのまま追加する提案はしない。現在使っている `RenderTargetBitmap` での明示的キャッシュが現実的。[現行Performance optimization](https://docs.avaloniaui.net/docs/app-development/performance)

**`UseRegionDirtyRectClipping`：** 過去の計測で効果がなかったことには理由があり得る。盤面サイズの明滅画像が残れば領域を分けても大きな矩形のまま。公式12.1の記事も、複数領域クリップがGPUによっては余分な描画より高価で、既定を無効へ変更したと説明している。「常に有効にする最適化」ではない。[Avalonia 12.1 rendering improvements](https://avaloniaui.net/blog/release-12-1)

**最新版への更新：** 12.1には描画データの転送時の割り当て削減などの改善があるが、このアプリのCPU問題の解決は保証されない。11.3.22での原因切り分けを先に行い、移行は別の比較実験として扱う。同じ公式12.1記事の改善のうち「透明でないWindowsサーフェス」の変更を、透明なMacの盤面の改善根拠にしない。

**ネイティブアニメーション：** AppleのCore Animationは、画像として保持されたレイヤーの位置や不透明度をハードウェアで合成する設計。玉の経路と明滅をOS側に移し、Avalonia本体を静止させる候補になる。ただしAvaloniaが管理するレイヤーへ無断で子を追加する実装は避け、所有権と寿命が明確なホストの技術検証が必要。移動、リサイズ、DPI、Hide/Show、グリッチ、クリック透過、スクリーンショットへの写り方を確認する。CPUがWindowServer/GPU側へ移ることもあるので、アプリCPUだけで成功判定しない。[Apple Core Animation Basics](https://developer.apple.com/library/archive/documentation/Cocoa/Conceptual/CoreAnimation_guide/CoreAnimationBasics/CoreAnimationBasics.html)

透明な別ウィンドウを増やす案も、そこがAvalonia Softwareで毎フレーム全体を転送するなら効果は限定的。別窓を作ること自体より、静止面と演出の再描画・転送を独立させることが目的。

## 5. 最短で結論を出す計測手順

1. **基準を固定する。** Release、同一盤面サイズ・項目数・背景・DPI・表示位置で、実更新fpsを確認。起動直後を除き、各条件30秒×3回。平均に加えてばらつきとフレーム時間も保存する。記録済みの8秒値とは分ける。
2. **dirty領域を可視化する。** 11.3.22に存在する `RendererDebugOverlays.DirtyRects` / `Fps` / `RenderTimeGraph` を診断時のみ利用。玉1個、玉2個、明滅、帯、全部で範囲を観察する。診断表示は描画条件そのものを変え得るので、最終CPU測定時には外す。
3. **静的発光の寄与を測る。** 玉だけ／帯だけの各構成で、静的な外側・内側の発光を診断用に外す。大きく下がれば画像化の優先度を裏付ける。外す実験と、見た目を保つ画像化実験は別に評価する。
4. **明滅の更新範囲を比較する。** 現状、分割だけ、regionだけ、分割＋regionの4条件。単独明滅と全部オンの両方を比較する。リング分割があっても既定の矩形unionでは範囲が縮まらない可能性を確かめる。
5. **実際にCPUを消費する場所を採取する。** macOSのTime Profiler等でUI更新、Skiaのpath/clip/blend、メモリ確保、全体コピーを分ける。マネージド割り当てだけのプロファイルではネイティブ描画・転送を見落とす。
6. **改善後にバックエンドを再比較する。** 同じ実fpsでSoftwareと利用可能なGPU経路を比較。アプリCPU、GPU、WindowServer、メモリ、表示遅延を記録する。差が小さければ現方式を維持する。

CPUは可能なら `100 × プロセスCPU時間の増分 / 実時間` を併記して1コア換算に揃える。**ユーザー確定方針（2026-10-07）は「負荷は可能な限り下げる。数値目標の設定は不要」。** 目標値の提示を求めず、特定のCPU使用率への到達を終了条件にしない。見た目・機能・滑らかさを維持し、小幅でも測定のばらつきと区別できる再現性のある改善を評価する。残る負荷の原因を測り、改善が見込める項目を順に検証する。

**今回確定したのは負荷を生む構造と改善候補であり、削減率ではない。** 静的発光の画像化後も転送が支配的なら、玉の数式やタイマーの微調整を続けるより、OS側レイヤーへの分離を検討する価値が高い。
